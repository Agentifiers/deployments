A platform installation runs in one AWS account and one region. An OpenTofu root calls the reusable platform stack, and the stack creates every component on this page. Read this page to learn what you deploy, which parts are optional, and how a request reaches the agent worker and comes back.

## One stack, many roots

Every OpenTofu root calls `infrastructure/modules/platform` as `module "platform"`, so every installation has the same resource addresses. A root gives the stack three kinds of input:

- The AWS account ID and region. The deploy tool passes them from your deployment target.
- A required `operations` object that sets the operational posture: deletion protection, availability, sizing, Fargate capacity, the web application firewall, search domain layout, public load balancers, operator shell access, test fixtures, retention periods, ops alert routing, the public API stage throttle (`public_api_throttle`), and per-organization limit defaults (`tenant_limit_defaults`). [Deploying the platform](/docs/operate/deployment#set-the-operational-posture) lists every field.
- Enable flags that turn whole components on or off.

A root also configures a second AWS provider with the alias `aws.us_east_1`. CloudFront accepts certificates only from us-east-1. The console distribution needs one, and so does the stream gateway distribution when the stream gateway has no dedicated load balancer.

### Turn components on

The customer root in `infrastructure/environments/customer` sets its own defaults, which turn on every component that needs no input only you can supply. The data layer has no flag. The tables below group the components by job. The source column names the repository path that holds the application code or the OpenTofu module.

### Network

The stack creates a VPC with public and private subnets, NAT egress for the private subnets, and gateway endpoints for S3 and DynamoDB on the private route tables.

## How an API request moves

1. A client sends an HTTPS request to the API custom domain.
2. The HTTP API matches the route. Exact routes send runtime, memory, and agent email operations to their Lambda functions. The `$default` route sends every other operation to the lifecycle API. Each integration has a 29-second timeout.
3. The Lambda function authorizes every request. It authenticates the bearer credential and checks scopes, roles, and the tenant scope headers. The HTTP API itself has no authorizer.
4. The function reads and writes DynamoDB and returns the response.

The identity service is a separate API on its own domain. It issues the tokens that clients then send to the public API. [Authentication](/docs/getting-started/authentication) describes the credential types.

## How an agent run moves

1. A run starts from the runtime API, a schedule or heartbeat that EventBridge Scheduler fires, a signed channel message that the inbound runtime picks up, an inbound email, or an evaluation. Each path records the run in DynamoDB and sends it to the FIFO run queue.
2. An agent worker task takes the run from the queue. It loads the deployment and its immutable release, the conversation history, and any memory the agent may recall.
3. The worker calls the model through the model gateway on the internal load balancer. The gateway checks a short-lived run token and forwards the call through Bifrost to the provider.
4. When the model selects a tool, the worker checks the call against the tool catalog and the tool's policy, then runs it. Provider and MCP tools also need an active connection. Sensitive tools can pause the run for approval. Code execution runs in a sandbox lease.
5. While the model generates, the worker writes token chunks to Durable Streams.
6. When the run finishes, the worker writes the assistant message, the run state, semantic events, and usage records to DynamoDB.

Clients read live output from the stream gateway. The runtime API issues a stream session, and the stream gateway checks it and proxies the read to Durable Streams over server-sent events or long polling. [Streaming](/docs/capabilities/streaming) describes the client side.

## Where state lives

The platform keeps its canonical state in DynamoDB. The data module creates six on-demand tables with point-in-time recovery.

| Table                   | Holds                                                                                                                                  | Stream |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| `control`               | Tenancy, principals, agent definitions, releases, deployments, brains, credentials, governance operations, and the installation record | no     |
| `execution`             | Threads, messages, runs, approvals, artifacts, sandbox leases, workflow executions, and inbox messages                                 | yes    |
| `events`                | Semantic events, audit events, idempotency records, and webhook deliveries                                                             | yes    |
| `usage`                 | Meter events, usage and cost counters, budgets, and rate-limit counters                                                                | yes    |
| `identity`              | Identity service records                                                                                                               | no     |
| `identity-email-outbox` | Pending identity emails                                                                                                                | yes    |

Other stores hold data that does not fit a table row:

| Store                                           | Holds                                                                               |
| ----------------------------------------------- | ----------------------------------------------------------------------------------- |
| A versioned S3 artifact bucket                  | Run artifacts, screenshots, and the Lambda release archives the deploy tool uploads |
| An S3 governance bucket with Object Lock        | Tenant exports and immutable audit exports                                          |
| Iceberg tables in S3 Tables                     | The semantic event history and, when enabled, observability history                 |
| OpenSearch                                      | Memory and brain search indexes                                                     |
| Amazon EFS                                      | Durable Streams data                                                                |
| Secrets Manager and SSM SecureString parameters | Service secrets and model provider keys                                             |

One customer managed KMS key, the platform data key, encrypts artifact and governance objects and the application's envelope encryption, including the credential vault. Separate KMS keys sign model gateway tokens, identity tokens, and audit export manifests.

## How events and usage stay consistent

A service writes a state change and its semantic event in one DynamoDB transaction. The event dispatcher reads the `events` table stream and publishes each event to the semantic EventBridge bus, so it can retry delivery without repeating the state change. Usage follows the same pattern. The worker writes meter events to the `usage` table, and a materializer reads the table stream and updates sharded counters. Meter records carry stable identities, so a replayed record does not count twice.
