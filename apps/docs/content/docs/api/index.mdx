The Deployments.ai API is a JSON-over-HTTPS API under the `/v1` path. Every capability on the platform is an operation in one OpenAPI 3.1 document. The TypeScript SDK is generated from that document, and the CLI is tested to cover every operation in it, so each operation has one SDK function and at least one CLI command.

## Base URL

Send requests to your install's API origin. These docs write it as the placeholder `https://api.example.com`; [Hosts and environments](/docs/getting-started/hosts-and-environments) explains where your install's origin comes from. Shell examples in these docs read it from `DEPLOYMENTS_API_URL`.

```sh
curl "$DEPLOYMENTS_API_URL/health"
```

The health check needs no credential and returns `{"status":"ok","service":"deployments-ai-api"}`. Reading a thread stream is the one operation served from another origin. Use the `streamUrl` the API returns. [Hosts and environments](/docs/getting-started/hosts-and-environments) lists every origin.

Fetch the live contract from `GET /v1/openapi.json`, or run:

```sh
deployments openapi --json
```

## Authenticate every request

Send a bearer credential in the `Authorization` header. A person uses a platform access token from sign-in. A service uses an API key that starts with `dpl_`. Most operations also need tenant headers that select the organization, project, or environment.

```sh
curl "$DEPLOYMENTS_API_URL/v1/agent-deployments" \
  --header "authorization: Bearer $DEPLOYMENTS_API_KEY" \
  --header "x-deployments-environment: $ENV_ID"
```

[Authentication](/docs/getting-started/authentication) explains the schemes, the device sign-in flow, and the tenant header rules.

## Request conventions

| Convention             | Rule                                                                                                                                                                                    |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bodies                 | Request and response bodies are JSON. A few operations stream bytes or Server-Sent Events, and their pages say so.                                                                      |
| IDs                    | Resource IDs are 26-character ULIDs in canonical uppercase Crockford base32.                                                                                                            |
| Timestamps             | Timestamps are UTC with millisecond precision, for example `2026-10-01T12:00:00.000Z`.                                                                                                  |
| Tenant headers         | `x-deployments-organization`, `x-deployments-project`, and `x-deployments-environment` select the tenant.                                                                               |
| Idempotency            | Most mutations take an `idempotency-key` header. See [Idempotency](/docs/api/idempotency).                                                                                              |
| Lists                  | Lists use `cursor` and `limit` query parameters and return `nextCursor`. See [Pagination](/docs/api/pagination).                                                                        |
| Optimistic concurrency | Updates to versioned resources, such as agent definitions and deployments, take the `expectedVersion` you last read. A stale version fails with status 409 and code `version_conflict`. |

## Response conventions

Successful responses return 200, 201, or 202. Each operation's page lists which one. A 202 means the platform accepted work that continues after the response, such as a run.

Failed responses use the problem details format with the `application/problem+json` media type. Problem responses carry an `x-request-id` header and repeat it in the body as `requestId`. Runtime, artifact, automation, and workflow execution operations are the exception. Their problem body includes `requestId` only when your request sent an `x-request-id` header. [Errors](/docs/api/errors) describes the format and common codes.
